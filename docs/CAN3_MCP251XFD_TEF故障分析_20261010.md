# CAN3 MCP251XFD TEF 故障分析记录

## 背景

机器人运行过程中出现如下错误：

```text
[taskset-2] [ERROR] [1791610748.029044937] [canfd_master]:
1 - CANFD send failed on can3: Resource temporarily unavailable
```

本次故障前已启动 `scripts/can.sh diag`，采集目录：

```text
/home/zoomlion/work/can_diag_20261010_133551/
```

采集信息包含：

- `dmesg_can.log`：内核 CAN/SPI/驱动相关日志
- `link_stats.log`：`ip -details -statistics link show can0~can3`
- `candump_error.log`：`candump -ta -e can0 can1 can2 can3`
- `socket_stats.log`：`/proc/net/can/stats`、`/proc/net/can/rcvlist_all` 等

## 结论摘要

这次数据可以基本定性为 **can3 底层 MCP2518FD/mcp251xfd 驱动或 SPI-CAN 控制器链路异常**，而不是上层运控程序先把 CAN 发送队列打满。

核心依据：

1. 内核驱动错误先发生，应用层 `send failed` 后发生。
2. can3 在驱动错误后 RX/TX 统计停止增长。
3. can3 的 BQL `inflight` 卡住不释放。
4. can3 仍保持 `ERROR-ACTIVE`，没有 bus-off、error-passive 或 CAN 总线错误计数增长。
5. 同一时间段 can0/can1/can2 继续正常收发。

因此，`Resource temporarily unavailable` 是 can3 底层 TX completion/资源回收异常后的应用层表现，不是根因。

## 关键时间线

应用层报错时间：

```text
1791610748.029 = 2026-10-10 13:39:08.029 CST
```

内核驱动异常时间：

```text
2026-10-10 13:38:53 CST
mcp251xfd spi4.0 can3: IRQ handler mcp251xfd_handle_tefif() returned -22.
mcp251xfd spi4.0 can3: IRQ handler returned -22 (intf=0x3f1a8016).
```

也就是说，mcp251xfd 的 TEF 中断处理异常比 `robot_driver` 的 `send failed` 早约 15 秒。

`candump` 中 can3 最后一帧时间：

```text
1791610732.957437 = 2026-10-10 13:38:52.957 CST
```

从 13:38:53 开始，can3 不再有帧；但 can0/can1/can2 继续正常输出到 13:39:19 之后。

## 关键证据

### 1. can3 驱动 TEF 异常

`dmesg_can.log`：

```text
[Sat Oct 10 13:38:53 2026] mcp251xfd spi4.0 can3:
IRQ handler mcp251xfd_handle_tefif() returned -22.
[Sat Oct 10 13:38:53 2026] mcp251xfd spi4.0 can3:
IRQ handler returned -22 (intf=0x3f1a8016).
```

`TEF` 是 MCP251xfd 的 TX Event FIFO，驱动依赖它确认发送完成并回收 TX 资源。这里返回 `-22` 表示驱动在处理 TX 完成事件时遇到非法状态或不符合预期的数据。

### 2. can3 未进入 bus-off

13:38:53 后，`link_stats.log` 中 can3 一直显示：

```text
can <FD,200> state ERROR-ACTIVE (berr-counter tx 0 rx 0) restart-ms 100
re-started bus-errors arbit-lost error-warn error-pass bus-off
0          0          0          0          0          0
```

说明：

- 没有 bus-off
- 没有 error-passive
- 没有 error-warning
- 没有 bus-errors 增长
- `restart-ms 100` 不会触发，因为该机制只处理 bus-off 自动恢复

### 3. can3 RX/TX 统计冻结

13:38:52：

```text
RX packets 1416513
TX packets 708263
bql_inflight=200
```

13:38:53 到 13:39:19：

```text
RX packets 1416513
TX packets 708263
bql_inflight=200
```

RX/TX 计数完全不再增长，BQL `inflight` 固定为 200，说明内核认为仍有未完成的发送数据，但 TX 完成事件没有正常回收。

### 4. can3 停止收发，但其他 CAN 正常

`candump_error.log` 全量统计：

```text
can0 1167050
can1 1167041
can2 1000361
can3 1017391
```

故障窗口内，can3 最后一帧停在：

```text
(1791610732.957437) can3 ...
```

而 can0/can1/can2 后续仍持续有帧输出到采集结束附近：

```text
can0 last 1791610759.678360
can1 last 1791610759.678269
can2 last 1791610759.678196
```

这说明异常是 can3 单路问题，不是整个应用、CPU 调度、ROS executor 或所有 CAN 通道同时失效。

## 因果链判断

本次故障的合理因果链为：

```text
mcp251xfd can3 TEF IRQ 处理异常
    ↓
can3 TX completion 无法正常回收
    ↓
can3 RX/TX 停止增长，BQL inflight 卡住
    ↓
robot_driver 继续向 can3 send
    ↓
内核返回 EAGAIN / Resource temporarily unavailable
```

因此，应用层日志：

```text
CANFD send failed on can3: Resource temporarily unavailable
```

是底层 can3 TX 资源不可用后的结果，不是最初原因。

## 为什么可以排除上层运控主因

当前证据不支持“上层运控程序发送太快导致队列满”作为主因：

1. 驱动 TEF 错误先于应用层 send failed。
2. can3 出错后没有 CAN 协议层错误计数增长。
3. can3 的 RX/TX 统计冻结，表现为底层通道停止工作，而不是普通队列逐步积压。
4. 其他 CAN 通道仍正常收发，说明不是整体控制周期或 CPU 调度失控。
5. 之前 worker 诊断中 `exchange` 耗时和调度周期均正常，没有错过周期。

更准确的定性是：

```text
上层程序触发 send 时暴露了错误；
底层 mcp251xfd/SPI-CAN 控制器链路已经提前进入异常状态。
```

## `restart-ms 100` 为什么没有生效

`restart-ms` 只对 CAN 控制器 bus-off 自动恢复生效。

本次故障中 can3 一直是：

```text
state ERROR-ACTIVE
bus-off 0
```

因此不会触发 bus-off restart。该配置不能恢复以下问题：

- TEF/TX completion 处理异常
- SPI 通讯异常
- MCP2518FD 控制器内部状态异常
- IRQ 处理异常
- 驱动 TX 资源回收卡死

## 已验证的恢复方式

现场验证：

```bash
sudo ip link set can3 down
sleep 0.2
sudo ip link set can3 up
```

可以恢复 can3。

这说明问题不需要整机重启即可恢复，`ip link down/up` 能重新初始化 can3 网络设备和 MCP2518FD 控制器状态。

但该动作会造成明显通讯中断，对双足人形机器人行走过程不能作为无感恢复手段，只适合作为故障后的兜底恢复。

## 优化建议

### 1. 优先排查底层 MCP2518FD/SPI/IRQ

重点排查 can3 对应链路：

- RK3588 SPI4 控制器
- MCP2518FD 芯片
- mcp251xfd 驱动版本
- can3 的 IRQ/INT 线
- SPI CLK/MOSI/MISO/CS 信号质量
- MCP2518FD 供电和地
- 运动过程中的电机干扰、线束振动和 EMI

### 2. 降低 SPI 频率做验证

本次初始化日志显示：

```text
mcp251xfd spi4.0 can3 ... m:12.00MHz rs:8.50MHz ...
```

建议将设备树中 MCP2518FD 的 `spi-max-frequency` 下调验证，例如：

```text
12MHz -> 8MHz -> 6MHz
```

如果降低 SPI 频率后故障显著减少或消失，说明 SPI 信号完整性或时序裕量不足。

### 3. 检查 mcp251xfd 驱动补丁

当前内核：

```text
Linux 6.1.141-rt36 PREEMPT_RT
```

建议检查 mcp251xfd 在 6.1 系列和 PREEMPT_RT 下是否有 TEF/TX FIFO 相关补丁。重点关键词：

- `mcp251xfd TEF`
- `mcp251xfd handle_tefif`
- `mcp251xfd returned -22`
- `mcp251xfd tx event fifo`
- `mcp251xfd PREEMPT_RT`

### 4. 应用层增加最小兜底恢复

虽然根因在底层，但应用层可以避免故障扩大。建议做最小机制，不做复杂状态机：

```text
同一路 canX 连续 2~3 次 EAGAIN/ENOBUFS
    ↓
暂停该路发送
    ↓
触发单路 canX down/up
    ↓
恢复后重新打开 socket 或重新初始化 CanfdMaster
```

注意：

- 不建议在实时 worker 线程里直接执行阻塞 shell 命令。
- 可由后台恢复线程或独立 can manager 执行 `ip link down/up`。
- 恢复期间上层应立即退出行走控制，进入保护/阻尼/安全状态。

### 5. 继续保留 `can.sh diag` 作为现场证据工具

后续如果再次复现，建议从启动前就运行：

```bash
./scripts/can.sh diag -i "can0 can1 can2 can3" -n 1
```

重点查看：

- `dmesg_can.log` 中是否仍为 `mcp251xfd_handle_tefif() returned -22`
- 是否总是 `spi4.0 can3`
- TEF 错误前后 `bql_inflight` 是否卡住
- can3 的 RX/TX 统计是否停止增长
- 是否存在 CAN 协议层 bus error 或 bus-off

## 后续判断标准

如果后续仍表现为：

```text
mcp251xfd_handle_tefif() returned -22
can3 ERROR-ACTIVE
bus-off 0
RX/TX packets 停止增长
bql_inflight 固定不释放
ip link down/up 可恢复
```

则可以继续定性为底层 SPI-CAN 控制器/驱动链路异常。

如果后续出现：

```text
bus-off > 0
bus-errors 增长
berr-counter tx/rx 增长
CAN error frame 大量出现
```

则需要转向 CANFD 物理层排查，例如终端电阻、线束、屏蔽、接地、data bitrate、收发器、电机 ACK 等。
