## 1. 背景与问题现象

行走中机器人出现"腿抖 + 偶发突然要倒"的体感，尤其踝关节"脚软"：踝突然失去刚度、无法抵抗外力，机体倾斜后电机以大力矩猛拉纠正，产生顿挫。

既往记录（业务知识库/历史诊断）把"脚软"根因归为**踝串并联空间转换在奇异点附近产生位置阶跃**。本次工作对该结论做了重新确诊，并落地了一个命令端的修复。

---

## 2. 诊断过程与根因（Phase 0 离线确诊）

### 2.1 最严重失衡事件的因果链（日志 20261021_114759，t≈503.3s）

从 recorder 的 `joint_commands.csv` / `joint_states.csv` 逐帧导出左踝（leg_l_5 踝俯仰、leg_l_6 踝侧倾）命令位置、实测力矩、机体角速度，得到清晰因果：

1. **命令突跳**：t=503.161s，leg_l_6 命令单帧跳变 **−0.361 rad**（前一帧 +0.4332 → 逐级 −0.125 / −0.215 / −0.361）。
2. **力矩衰减 + 机体加速旋转**：503.28–503.35s，|w| 峰值达 77.5 rad/s。
3. **力矩塌零**：503.37s，leg_l_6 力矩从 ~20 Nm 塌到 −0.6 Nm。

因果延迟约 150–200ms。**命令突跳是因，力矩塌陷与机体倾斜是果**，并非电机本体故障。

### 2.2 关键更正：本次配置根本不跑串并联转换

检查运行日志 `20261021_114759/zl_robot.log`：

| 行 | 证据 | 含义 |
|----|------|------|
| 5 | `Hardware profile: tienkung` | 真机 |
| 59 | `tienkung worker SCHED_FIFO priority=70 enabled` | 实时线程正常 |
| 60 | `onnx runtime options for z01_pa_walk` | 模型是 z01_pa_walk（**并联踝**，非 z01_std_walk） |
| 61 | `ankle_in_series fast-forward: true -> false` | `ankle_in_series=false` |

代入 `robot_control_node.cpp::publishHardwareCommands` 的两个转换分支：

- `cmd.ankle_in_series && ankle_env_parallel_` → `false && true` = **false**
- `!cmd.ankle_in_series && !ankle_env_parallel_` → `true && false` = **false**

**两个分支都不成立 → 本次运行完全没有执行踝串并联 FK/IK 转换。** 因此"串并联转换奇异点"对本配置（z01_pa_walk 并联踝 + 真机）**不适用**，此前根因判断需更正。

> 补充：命令路径（S2P）本就用 FK 闭式解；带 `J.inverse()` 奇异爆炸风险的 Newton IK 只在状态反馈路径（P2S）。即便如此，本配置两者都未触发。

### 2.3 真正根因：50Hz ZOH 无插值下发 + 策略帧间尖峰

阅读 `rl_manager_node.py`：

- RL 推理 **50Hz**，命令发布 **200Hz**。
- `_handle_command_publish_timer` 只是把 `_latest_commands` 改 sequence/stamp **原样重发** = **零阶保持(ZOH)**，无插值。
- `_smoother`（OutputSmoother）只在**模型切换**的 10 帧生效，正常行走不介入。

因此策略每 20ms 一帧的位置输出，在两次推理之间被"平台式"保持，**策略帧间的任何位置差都变成瞬时阶跃直达电机**。在 200Hz 命令流上表现为典型阶梯（同一值保持 4 帧）。这与历史经验一致：**RL 命令端瞬时尖峰被高 kp 放大成力矩爆发/抖动，应修命令源头平滑性，而非擅调 RL 绑定增益或降 kp。**

## 3. 修复方案：A1 命令插值下发

### 3.1 设计

把 200Hz 命令发布从 ZOH 改为**线性插值**：每当 50Hz 推理产出新目标，200Hz 定时器用 4 帧（200/50）从"上一帧已发布位置"线性斜坡到新目标，使单帧位置变化降到约 1/4。

### 3.2 实现（`src/robot_rl_manager/robot_rl_manager/rl_manager_node.py`）

- 新增纯逻辑类 `CommandInterpolator`（line 120）：`set_target()` / `next_positions()` / `mark_published()` / `reset()`。
  - `next_positions()` 按 `alpha = frame/total` 线性插值，`alpha>1` 饱和保持目标；起止长度不一致时直接返回目标（安全兜底）；首帧无基线时不产生运动。
- 新增参数（line 196–197）：
  - `enable_command_interpolation`（默认 `True`）
  - `command_interpolation_frames`（默认 `0` = 自动 `round(发布频率/推理频率)` = 200/50 = 4）
- `__init__`（line 265–266）：按参数或自动值构造插值器，保存 `_interp_publish_msg`。
- `_set_latest_commands`：`deepcopy` 捕获插值目标（副本，避免与 ZOH 消息互相污染）。
- `_handle_command_publish_timer`：**仅 TYPE_RUN** 走插值发布；TYPE_PREPARE 保持原 ZOH 语义（交给 robot_control 的准备插值，不叠加）。

### 3.3 安全/接口边界（对齐 AGENTS.md Hard Invariants）

- **不改** topic/service/消息类型/字段语义/QoS/参数默认对外语义。
- **不改** 关节名称/顺序/单位/索引/映射/坐标空间转换。
- **不改** 控制频率(50/200Hz)、线程模型（单线程执行器 `rclpy.spin`）、callback group、队列深度。
- **不碰** kp/kd、RL 模型输入输出语义、推理频率。
- 插值只作用于命令发布环节的位置序列，PREPARE/急停/阻尼/限幅等安全路径语义不变。
- 提供 `enable_command_interpolation` 开关，可一键回退到原 ZOH 行为。

## 6. 专项分析：155038 的严重失衡来自哪

针对"命令平滑却仍剧烈失衡"的 155038，逐帧定位（t≈129.93→130.17s，约 0.25s 一次 violent 事件）：

| 阶段 | 证据 | 含义 |
|------|------|------|
| ① 触发 129.93 | 左膝 leg_l_4 速度突跳 +11.2 rad/s、左踝 leg_l_6 +9~10 rad/s，**命令无台阶** | 左腿被外力"甩动"（脚滑/绊/被推），非电机指令引起 |
| ② 发散 | 实测位置迅速偏离平滑命令，跟踪误差冲到 0.5–0.8 rad | 关节跟不上，PD 误差被放大 |
| ③ 暴力救场 | 左髋 leg_l_1 力矩峰值 **183 Nm**（26 帧 >120 Nm）、左膝 **−176 Nm**，深度饱和 | 电机砸到接近上限仍拉不住 → 左膝屈曲失稳 |
| ④ 机体震荡 | \|w\| 多次摆动 166→216→240→**265** rad/s | 濒摔 + 反复挣扎恢复，最终未触发硬故障 |

**命令层已洗清**：起振窗口内所有关节命令单帧跳变最大仅 leg_l_5 的 **0.337 rad（67 rad/s）**，踝 ≤0.20（41 rad/s），远低于改前的 0.876 rad（175 rad/s）。

**结论**：155038 的剧烈失衡是**左腿受到外部机械扰动（最可能脚底打滑/失去牵引，或绊到/被碰）→ 高增益控制器以饱和力矩暴力补偿 → 机体多次震荡**的物理过程，**不是命令台阶**。插值及任何命令端手段都无法阻止它。它与历史"暴力补偿"机制一致（跟踪误差被高 kp 放大），区别在**误差源是物理扰动而非命令尖峰**。

**边界**：仅凭日志无法 100% 区分"外部打滑/碰撞"与"策略自激失稳"，但"关节速度先突跳、力矩后饱和、命令全程平滑"的先后顺序强烈指向外部机械触发；坐实需脚底接触力/地面真值或当时视频。

## 7. 结论

1. **根因更正**：z01_pa_walk 并联踝 + 真机配置下**不跑串并联转换**，"脚软"根因不是奇异点，而是 **50Hz→200Hz 的 ZOH 无插值下发**把策略帧间位置差变成瞬时阶跃直达电机，被高 kp 放大。
2. **修复有效（命令层与抖动层）**：A1 插值把踝命令速率降约 8×、髋力矩 jerk 中位减半、踝力矩塌陷极端值消失，与用户体感一致。
3. **严重失衡非命令所致**：如 155038 的 \|w\|=265 事件是外部机械扰动 + 饱和力矩暴力补偿，属抗扰/恢复鲁棒性问题，插值无法覆盖。

---

## 8. 后续建议

1. **受控 A/B**（最该做）：同操作员/同路径，`enable_command_interpolation` false/true 背靠背各走一遍，排除运行强度混淆，量化对"要倒"的真实影响。
2. **降延迟**：若 A/B 显示延迟不利，把 `command_interpolation_frames` 设为 **2**（延迟减半、台阶仍降一半）。
3. **换机制备选**：用**纯速率限幅**（仅削超阈值单帧跳变、正常跟踪零延迟）替代"斜坡到目标"，兼顾少抖与低延迟——与历史经验"命令速率限幅优于调 kp/kd"一致。
4. **抗扰方向**（针对 155038 类事件）：排查 t≈130s 是否在转弯/加速导致左脚打滑；评估输出力矩速率限幅以软化暴力补偿；本质属策略/安全层鲁棒性。
5. **勿擅动 RL 绑定 kp/kd**：历史已验证真机擅改增益会全面恶化。

## 附：分析方法与可复用要点

- recorder CSV 列名以 `_<suffix>` 结尾（如 `leg_l_6_pos` / `_tor` / `_vel`），用后缀建"关节名→列索引"映射解析。
- 命令/状态两文件时间基准可能不同，跨文件对齐用最近邻戳匹配，勿用精确相等。
- 部分 CSV 含 NUL 字节（异常/未写完），读取时先 `read().replace(b'\x00', b'')` 再解析。
- 判断插值是否生效的稳健指纹：命令"连续相等帧 run-length"（ZOH≈4，插值≈1）。
- 效果对比务必多轮 + 按总分钟归一化，单轮对比易被运行强度偶然性误导。
